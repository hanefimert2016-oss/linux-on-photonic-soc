# Architecture deep-dive

This document expands on the high-level diagram in the [main README](../README.md)
and explains design choices that may not be obvious to someone reading the
RTL/Python directly for the first time.

## SoC composition

The SoC is generated by **LiteX**, a Migen-based hardware description
framework. The Python script [`sim/sim_linux.py`](../sim/sim_linux.py)
instantiates `PhotonicSoCLinux`, a subclass of `litex.soc.integration.SoCCore`.

The major pieces:

| Block | Implementation | Origin |
|-------|----------------|--------|
| CPU | `VexRiscv-SMP`, `linux` variant | upstream `pythondata-cpu-vexriscv-smp` |
| ROM (BIOS) | LiteX BIOS, 64 KiB integrated | upstream LiteX |
| Main RAM | `SDRAMPHYModel` (64 MiB, behavioural) | upstream LiteDRAM |
| UART | `sim` (serial2console) | upstream LiteX sim |
| Interrupts | RISC-V PLIC + CLINT | upstream LiteX/VexRiscv |
| Custom | `wdm_fabric` (this repo) | `rtl/wdm_fabric.v` |

The CPU's reset vector is set to the LiteX BIOS in ROM. After self-test the
BIOS reads `ROM_BOOT_ADDRESS = 0x40f00000` (the OpenSBI base) and chain-loads
into RISC-V machine-mode firmware.

## Boot chain

```
                         power-on
                            |
                            v
+--------------------------------------------------------+
|  LiteX BIOS (in ROM)                                   |
|  - prints SoC banner / SDRAM init                      |
|  - waits ~3 s for serial-boot magic; then jumps to     |
|    ROM_BOOT_ADDRESS = 0x40f00000                       |
+--------------------------------------------------------+
                            |
                            v
+--------------------------------------------------------+
|  OpenSBI v0.8 (M-mode)        @ 0x40f00000             |
|  - sets up RISC-V SBI                                  |
|  - hands off to S-mode kernel at 0x40000000            |
+--------------------------------------------------------+
                            |
                            v
+--------------------------------------------------------+
|  Linux 5.14 (S-mode)          @ 0x40000000             |
|  - DTB at 0x40ef0000 (rv32.dtb)                        |
|  - rootfs at 0x41000000 (rootfs.cpio, ramfs)           |
|  - liteuart driver gives `console=liteuart`            |
+--------------------------------------------------------+
                            |
                            v
                    `buildroot login:`
```

The pre-built OpenSBI/Linux/dtb/rootfs come from upstream
[linux-on-litex-vexriscv issue #164](https://github.com/litex-hub/linux-on-litex-vexriscv/issues/164),
fetched by `scripts/fetch_images.sh`. They are loaded into the SDRAM model at
build time via `boot_ram0.json`, which is why the simulator can reach
`Liftoff!` without needing to push anything over UART.

## The WDM fabric

The photonic-inspired fabric is an HDL behavioural model of an N-channel
parallel data link. It is intentionally simple so that:

* it synthesises cleanly on small FPGAs (no Verilog 2009-only constructs),
* the waveform diagram makes the architectural point at a glance,
* it can be stitched into the LiteX SoC as a normal AXI / wishbone slave
  later, without changes to the cores themselves.

```
   +----------------------------+      +----------------------------+
   |  wdm_scheduler             |      |  wdm_fabric                |
   |                            |      |                            |
   |  emits a unique payload    |  ==> |  passes each lambda's      |
   |  on each lambda every      |      |  payload to its own RX      |
   |  clock edge                |      |  output (zero contention)  |
   +----------------------------+      +----------------------------+
                                                   |
                                                   v
                                          +-----------------+
                                          |  rx_data[k],     |
                                          |  rx_valid[k]    |
                                          +-----------------+
```

* `wdm_fabric` exposes a `tx_*` / `rx_*` valid-ready interface per lambda.
  Because each wavelength is independent, `tx_ready` is always asserted out
  of reset.
* `total_words` is incremented by the number of *simultaneous* successful
  transfers per cycle, so on every active cycle it grows by `NUM_LAMBDAS`.
  This is the on-chip equivalent of the aggregate-throughput counter you'd
  see on a real photonic transceiver.

### Default parameters

| Parameter      | Default | Notes |
|----------------|---------|-------|
| `NUM_LAMBDAS`  | 8       | number of parallel wavelength channels |
| `DATA_WIDTH`   | 32      | bits per channel per cycle              |
| `CLK_PERIOD`   | 10 ns   | testbench clock = 100 MHz simulated    |
| `SIM_CYCLES`   | 256     | cycles of activity per testbench run   |

At the defaults, 256 cycles × 8 lambdas → 2048 32-bit words written into the
fabric, and the testbench fails the run if it sees fewer than `(SIM_CYCLES-4)
× NUM_LAMBDAS` (i.e. it tolerates the 4-cycle reset / enable ramp).

## FPGA portability

The HDL is plain Verilog-2001 with no vendor-specific constructs:

* No DSP-block primitives.
* No instantiated SerDes / GTH / GTH4 / etc.
* Synchronous reset, single clock domain.

So it should drop straight onto any of the boards LiteX already supports
(Arty A7, ECP5, Versa-ECP5, OrangeCrab, Tang-Primer, Colorlight 5A-75B,
Sipeed-Tang, Ulx3s, …). The LiteX SoC scaffolding around it is identical to
the upstream `linux-on-litex-vexriscv` design, so the same bitstream that
boots Linux on those boards can carry the WDM fabric as an extra peripheral.

## Why this isn't (and doesn't pretend to be) a real photonic chip

A real WDM photonic interconnect needs:

| Component                          | Realised here?       |
|------------------------------------|----------------------|
| Multi-wavelength laser source       | ❌ no — pure RTL    |
| Mach-Zehnder / ring modulators      | ❌ no               |
| Waveguide                           | ❌ no — bus wires   |
| Wavelength (de)multiplexer (AWG)   | ❌ no               |
| Photodetector + TIA per channel    | ❌ no               |
| **Architectural pattern: N independent parallel lanes** | ✅ yes |
| **Throughput scales linearly with N** | ✅ yes |
| **Synthesisable, FPGA-portable**   | ✅ yes              |

The repository's value is the last three rows. If you ever do tape out a
photonic ASIC, the digital "fabric" side of it would look very much like
[`rtl/wdm_fabric.v`](../rtl/wdm_fabric.v) — that is the part Verilog can
genuinely express.
